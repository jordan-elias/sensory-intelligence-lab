Privacy Policy

Your data belongs to you.

Privacy is not a feature added at the end — it is the starting point of how this platform was built. This document explains in plain language what data is collected, how it is stored, how it is protected, and what you can do with it. Technical detail is included deliberately, because vague reassurances are not reassuring.

If something here is unclear, or if you have a question not answered below, write to hello@jordanelias.de. You will get a direct reply.

Your content and your privacy

The journal, check-in notes, and worksheets are personal tools. The platform is built around a simple principle: nothing is recorded unless you actively choose to save it. You are always in control of what happens to what you write.

The three options — and what each means for your data Save encrypted — your entry is encrypted in your browser before being sent to the server. The platform stores ciphertext only. Only you can decrypt and read it in a future session.

Download as a file — your entry is written directly to a file on your own device. Nothing is sent to any server at any point. The platform has no record that you wrote anything. The file belongs entirely to you.

Delete / Destroy — the text is permanently erased from the page and from memory. Nothing is sent anywhere. Nothing is logged. It is gone completely.

Writing, downloading, and deleting are completely private in every case. No data is collected during the writing process. No drafts are auto-saved to the server. No keystroke or word count data is transmitted while you are writing. The only moment any content leaves your browser is when you explicitly press Save — and at that point it is already encrypted.

How encryption works

When you choose to save content, it is encrypted in your browser before it is sent to any server. What is stored in the database is ciphertext: scrambled data that cannot be read without the correct key.

The encryption standard

All content encryption uses AES-256-GCM (Advanced Encryption Standard, 256-bit key, Galois/Counter Mode). This is the same standard used by banks, governments, and end-to-end encrypted messaging applications. GCM mode provides both confidentiality (the content cannot be read) and integrity (any tampering with the ciphertext is detectable).

Technical specification

Algorithm: AES-256-GCM

Key length: 256 bits (32 bytes)

IV (Initialisation Vector): 96 bits (12 bytes), randomly generated per encryption operation — every save produces a unique ciphertext even for identical content

Implementation: Web Crypto API (window.crypto.subtle) — browser-native, no external libraries

Storage format: JSON object containing base64-encoded IV and ciphertext, stored as a text column in Supabase

When encryption happens: In your browser, before any data is transmitted. Plaintext never travels over the network.

Your encryption key

Each account has a unique AES-256 encryption key, generated when you first visit a module that uses encryption (journal, check-in notes, worksheets). This key is generated on our server and returned to your browser over HTTPS, where it is held in memory for the duration of your session only. It is never written to localStorage, cookies, or any other persistent browser storage. When you sign out or close the tab, the key is gone from your device.

The key is stored in the database in an encrypted form, wrapped using a key derived from a platform secret — a random value stored only in our server environment variables, never in the database. When you sign in, our server verifies your identity and uses the platform secret to unwrap your key and return it to your browser.

What this means honestly

Honest limitation This model protects saved data against database breaches — if someone obtained a copy of the database, they would see only ciphertext that cannot be decrypted without also compromising the server environment. However, as the platform operator, Jordan Elias has access to the platform secret. This means that, in theory, someone with access to both the database and the server environment could decrypt saved content.

This is disclosed because honest privacy policy matters more than false reassurance. If you want absolute certainty that no one can read what you write, use the download or delete options — in both cases nothing is stored anywhere.
What this protects against A database breach alone cannot expose your saved entries. They are ciphertext without the server secret. Your data is never stored or logged in plaintext anywhere in the system.

The future upgrade path

The architecture is designed to support an upgrade to true end-to-end encryption in a future version, where your key would be derived from a passphrase only you know — making decryption impossible even for the platform operator. This upgrade path is built into the codebase but not yet activated. It will be announced clearly when available, and upgrading will be opt-in with no loss of existing data.

Identity separation

Your identity — email address and name — is stored separately from your content. Supabase maintains a dedicated auth.users table for authentication data, separate from all content tables. All content tables reference you only by a UUID — a random string like a3f2c1d4-... — not by your name or email. Someone who obtained only the content tables would see encrypted ciphertext attached to anonymous identifiers.

Supabase and the database

This platform uses Supabase as its database and authentication provider — an open-source alternative to Firebase, built on PostgreSQL and hosted on AWS. The database is in the EU West (Frankfurt) region, keeping all stored data within the European Union.

Row Level Security (RLS)

Every table has Row Level Security enabled. RLS is a PostgreSQL feature that enforces access control at the database level — not just in application code. Even if there were a bug in the application, the database itself would refuse to return data the requesting user is not authorised to see.

RLS policy structure

journal_entries: Users can only read, create, and delete rows where user_id = auth.uid(). No other user can access another user's entries via the API.

checkins: Same pattern — rows are visible only to the user who created them.

worksheets: Same pattern — each worksheet row is locked to its creator's user ID.

profiles: Users can read and update only their own profile row. Encryption key columns cannot be read by any application-layer query other than the dedicated vault server function.

The service role key

Supabase provides two API keys: an anon key (used in the browser, subject to RLS) and a service role key (bypasses RLS, for server use only). The service role key is stored only in Netlify environment variables and is never exposed to the browser. The vault function that handles encryption keys uses the service role key only after verifying the user's session token.
